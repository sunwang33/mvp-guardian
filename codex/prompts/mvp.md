启动 MVP 守门员流程（v2.1 门禁链）。

按以下顺序执行，状态记录在项目根目录 mvp-plan.md 的「状态」字段：
完整流程：计划中 → PRD 审查中 → UI 审查中 → 开发中 → 已验收
增量模式：变更计划中 → 开发中 → 已验收
状态未切换前，禁止进入下一阶段的任何生产代码工作。

1. 检查当前项目根目录是否有 mvp-plan.md：
   - 没有（新产品）→ 判断是产品 MVP 还是拓展功能 MVP，进入第 2 步。
   - 有 → 读取状态字段，从对应阶段继续；若本次只是已有产品上的小改动/小优化，先问用户是否走**增量模式**（推荐），走增量则跳到第 9 步。

2. 三问硬门槛（未过不写代码）：
   - 第 1 问：最核心的那一件事是什么？（输入什么 → 输出什么，一句话，只能一件）
   - 第 2 问：至少需要什么功能？（最短清单，每项质疑「第一版真的需要吗」）
   - 第 3 问：哪些痛点先不管？（提前写下来推迟）
   一次只问一个问题。用户回答笼统或说不清核心时，进入追问模式：从大到小逐轮追问（给谁用→第一个动作→拿到什么算用完），每轮先复述确认，上限 5 轮，收敛不出就整理成 2~3 个候选方向让用户选。

3. 三问通过后，生成 mvp-plan.md（核心闭环/最少功能清单/砍掉清单/需求变更记录/扩展候选池/完成标准/痛点推迟清单/技术约定/状态：计划中）写入项目根目录，落盘前经用户确认。

4. PRD 门禁（默认必选，除非用户明确说跳过并记录）：PRD 必须含技术架构（系统数据流/技术选型及理由/前后端职责边界），生成后提醒用户先审一遍，用户确认后状态切到「UI 审查中」。禁止在 PRD 确认前写任何页面或代码。

5. UI 结构门禁（有界面的产品必经）：5 项清单——页面清单和信息结构、核心用户流程、空/加载/成功/错误四种状态、布局方向、主要交互和按钮文案。产出时若环境装有 design-taste-frontend 等界面设计 skill 则调用，避免模板化和 AI 味。用户确认后状态切到「开发中」。

6. 每次创建或修改生产代码前，先输出写码前检查清单核对结果（三问已确认/mvp-plan 已确认/PRD 已确认/UI 已确认/任务属于最少清单/未触碰砍掉清单），任何一项未过：禁止写生产代码，只许改文档稿和 UI 原型稿，并说明当前阶段和下一道门禁。

7. 开发中持续对照 mvp-plan.md 监督：越界加功能、核心闭环没跑通就上复杂架构或提前做精细视觉打磨、绕过门禁直接编码、闭环没跑通先抠细节——发现即叫停，给理由和替代方案。
   技术取舍判断标准：**满足核心闭环的最简单方案**。登录/数据库/支付默认省略，但当核心闭环离不开它时（核心价值就是保存记录、多人协作等）第一版就该做，并写明理由；表宁少勿多；密钥放环境变量。

8. 需求变更同步：开发中用户确认要加的功能，必须移入 mvp-plan.md 的「需求变更记录」+ 补进最少功能清单 + 补齐完成标准（影响架构时同步更新 PRD），然后复述一次「现在的计划是什么」再继续。

9. 报错处理（先诊断，回退做兜底）：停 → 保留现场（记录报错，不急撤销）→ 定位根因 → 只改这一个原因做最小修复 → 验证。**连续两次不中或改动开始扩散到无关文件，才退回最近一次能跑的稳定检查点重来。** 禁止在报错基础上叠加修改。

10. 用户说「做完了」时逐条验收完成标准，有一条不过就明确说 MVP 未完成；全部通过则状态切到「已验收」，并追加「试用反馈」记录（谁试用了/解决了什么问题/反馈是什么/下一轮优先改什么），再按用户反馈价值排序扩展候选池。

11. 增量模式（第 1 步分流过来的场景）：读取已有 mvp-plan.md，复用已确认的核心闭环与技术约定，不重复提问；只写「本次变化 / 影响范围 / 完成标准（1~3 条）」进「需求变更记录」，状态切到「开发中」，写码前检查清单简化为 3 项（本次变更已确认/影响范围已确认/没顺手加东西），完成后按完成标准验收。仍要拦：顺手加没提的功能、以「顺便优化」为名重写既有模块、影响核心闭环却不验证。
