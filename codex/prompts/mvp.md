启动 MVP 守门员流程（v2.2：先分档 → 阶段门禁链）。

**第 0 步：分档并说出判断**（做第一个提问之前完成，让用户可以推翻）：
- **快速验证档**——「能不能做 X」的可行性问题（模型/接口/库行不行）→ 走第 14 步
- **增量档**——已有产品上的小改动、小优化，且项目里已有可读的流程 → 走第 13 步
- **完整档**——新产品、新功能模块、结构级改动 → 走第 1 步
判据是项目而非熟悉度（新项目没有可读的既有流程，一律完整档）；拿不准选更重的档；中途发现复杂度超预期只能升级档位，**永不降级**。

状态记录在项目根目录 mvp-plan.md 的「状态」字段：
完整档：计划中 → PRD 审查中 → UI 审查中 → 开发中 → 已验收
增量档：变更计划中 → 开发中 → 已验收
状态未切换前，禁止进入下一阶段的任何生产代码工作。（快速验证档不落盘、不进状态机）

1. 检查当前项目根目录是否有 mvp-plan.md：
   - 没有（新产品）→ 判断是产品 MVP 还是拓展功能 MVP，进入第 2 步。
   - 有 → 读取状态字段，从对应阶段继续；若本次只是已有产品上的小改动/小优化，先问用户是否走**增量档**（推荐），走增量则跳到第 13 步。

2. 前置自检：若需求里出现**多个互相独立的子系统**（如「带聊天、文件存储、计费、分析的平台」），先停下来说明「这是几件独立的事」，帮用户拆开（各自是什么、怎么关联、先做哪个），只挑第一块走完整流程——不要在需要先拆解的项目上细化细节。

3. 三问硬门槛（未过不写代码）：
   - 第 1 问：最核心的那一件事是什么？（输入什么 → 输出什么，一句话，只能一件）
   - 第 2 问：至少需要什么功能？（最短清单，每项质疑「第一版真的需要吗」）
   - 第 3 问：哪些痛点先不管？（提前写下来推迟）
   一次只问一个问题。**每次收到回答先复述你理解的版本，并分开写「用户说的」与「我替你补的假设」，用户确认后再往下。**
   用户回答笼统或说不清核心时，进入追问模式：从大到小逐轮追问（给谁用→第一个动作→拿到什么算用完），每轮复述确认（含区分假设），上限 5 轮，收敛不出就整理成 2~3 个候选方向让用户选（可附取舍与推荐）。

4. 三问通过后，生成 mvp-plan.md（核心闭环/最少功能清单/砍掉清单/需求变更记录/扩展候选池/完成标准/痛点推迟清单/技术约定/状态：计划中）写入项目根目录，落盘前经用户确认。

5. PRD 门禁（默认必选，除非用户明确说跳过并记录）：PRD 必须含技术架构（系统数据流/技术选型及理由/前后端职责边界）。**生成后先自己做四项自审并输出结果**——①占位符扫描（TBD/TODO/含糊表述）②内部一致性（章节矛盾、架构与功能是否对得上）③范围检查（是否锁在最少功能清单内，没偷塞候选池功能）④歧义检查（有无能被两种方式理解的需求）。自审结果连同 PRD 交给用户，请用户再审一遍；用户确认后状态切到「UI 审查中」。禁止在 PRD 确认前写任何页面或代码。

6. UI 结构门禁（有界面的产品必经）：5 项清单——页面清单和信息结构、核心用户流程、空/加载/成功/错误四种状态、布局方向、主要交互和按钮文案。产出时若环境装有 design-taste-frontend 等界面设计 skill 则调用，避免模板化和 AI 味。用户确认后状态切到「开发中」。

7. **阶段授权不传递**：一次点头只授权它被呈现的那一个阶段——批准 mvp-plan ≠ 批准 PRD ≠ 批准 UI ≠ 可以写清单外的代码；「想法不错」「方向对」这类回应不算批准。门禁未完成期间只允许只读探索和修改文档稿/原型稿。

8. 状态切换为「开发中」后的第一条回复，先完整输出写码前检查清单核对结果（三问已确认/mvp-plan 已确认/PRD 已确认/UI 已确认/任务属于最少清单/未触碰砍掉清单，用一段话自报），然后才允许执行任何命令、写入任何文件、安装任何依赖——搭骨架、装依赖、改配置同样排在清单之后。任何一项未过：禁止写生产代码，只许改文档稿和 UI 原型稿，并说明当前阶段和下一道门禁。

9. 开发中持续对照 mvp-plan.md 监督。**自我合理化对照表**（左列是危险念头，命中任意一条立刻停下说明）：
   - 「这太简单了不用走流程」→ 走流程成本是几句话，跳流程成本是返工
   - 「先写点代码看看效果，回头补计划」→ 这是跳阶段，PRD/UI 未确认不许动生产代码
   - 「先搭骨架、装依赖，这不算写代码」→ 骨架、依赖、配置都是实现的一部分，检查清单先于这一切
   - 「我已经理解需求了，不用再问」→ 理解要写出来让用户确认
   - 「顺手把 XX 也加上」→ 清单外功能一律进扩展候选池
   - 「核心没跑通但先把界面做漂亮」→ 视觉打磨在痛点推迟清单里
   - 「完成标准差不多满足了，算完成吧」→ 逐条核对 + 给证据，差一条就是没完成
   - 「报错了，我多改几处试试」→ 先诊断、留现场、最小修复一次
   - 「用户说方向对，可以继续下一步」→ 一次点头只覆盖一个阶段
   - 「试验跑通了，这段代码就留着用」→ 快速验证产物是结论，留代码要重新分档
   叫停时给三样东西：为什么拦、依据（mvp-plan 哪一条/哪道门禁/哪个档位）、下一步建议。
   技术取舍判断标准：**满足核心闭环的最简单方案**。登录/数据库/支付默认省略，但当核心闭环离不开它时（核心价值就是保存记录、多人协作等）第一版就该做，并写明理由；表宁少勿多；密钥放环境变量。

10. 需求变更同步：开发中用户确认要加的功能，必须移入 mvp-plan.md 的「需求变更记录」+ 补进最少功能清单 + 补齐完成标准（影响架构时同步更新 PRD），然后复述一次「现在的计划是什么」再继续。

11. 报错处理（先诊断，回退做兜底）：停 → 保留现场（记录报错，不急撤销）→ 定位根因 → 只改这一个原因做最小修复 → 验证。**连续两次不中或改动开始扩散到无关文件，才退回最近一次能跑的稳定检查点重来。** 禁止在报错基础上叠加修改。

12. 用户说「做完了」时逐条验收完成标准，有一条不过就明确说 MVP 未完成；全部通过则状态切到「已验收」，并追加「试用反馈」记录（谁试用了/解决了什么问题/反馈是什么/下一轮优先改什么），再按用户反馈价值排序扩展候选池。

13. 增量档（第 0 步/第 1 步分流过来的场景）：读取已有 mvp-plan.md，复用已确认的核心闭环与技术约定，不重复提问；只写「本次变化 / 影响范围 / 完成标准（1~3 条）」进「需求变更记录」，状态切到「开发中」，写码前检查清单简化为 3 项（本次变更已确认/影响范围已确认/没顺手加东西），完成后按完成标准验收。仍要拦：顺手加没提的功能、以「顺便优化」为名重写既有模块、影响核心闭环却不验证。

14. 快速验证档（第 0 步分流过来的场景）：不写 mvp-plan、不问三问、不出 PRD。用 2~3 句话说明「要验证什么问题 + 打算怎么最省地试 + 试完得出什么判断」→ 用户点头 → 用最便宜的方式试（手搓提示词/一条 curl/十几行脚本）→ 报结论三选一：**能做**（附代价）/ **做不了**（附原因）/ **能做但很贵**（附替代方案）。试验代码标注「一次性，不进产品」。禁止顺手把试验代码填进产品、禁止以「验证」为名搭产品骨架；要落地就明确说「接下来走完整档或增量档」，重新过对应流程。
