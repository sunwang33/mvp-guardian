# MVP 原则参考

本文件是 mvp-guardian skill 的理论依据，内容为 sunwang33 在实战营学习与自己做项目过程中的实践总结与踩坑所得，非课程材料搬运。监督与建议时引用这些经验。

## 1. 开发前的三个问题（来源：学习笔记·需求梳理）

动手之前，先想清楚三件事：

1. 这个产品**最核心**的那一件事是什么？（一句话说清输入和输出。比如一个文字翻译工具，就是输入一段文字、输出译文。）
2. 至少需要什么功能？（列最短清单：什么输入、什么触发、什么输出。）
3. 还有哪些影响体验的痛点？（这些等 MVP 跑通之后再说。）

一句话原则：**先把闭环跑通，再谈完美。**

## 2. 开发流程顺序（来源：学习笔记·开发思路）

1. 明确需求
2. 生成 PRD 文档
3. 生成 UI 初稿
4. 代码生成（第一小步先写框架）
5. 调试迭代
6. 部署上线

配套提醒：

- UI 设计参考图很重要。
- **不要着急写代码。**
- **第一版不要贪多，先跑通再说。**

## 3. 经验教训（来源：自己的踩坑记录）

- **报错要及时止损**：AI 开发过程中一旦报错，别在错误代码上继续叠加修改，会错上加错。v2.1 起细化为「先诊断最小修复，连改不中再回退」，见第 9 节。
- **PRD 自己先审一遍**：生成 PRD 后先看有没有遗漏、AI 是否理解到位，立刻修改，省 token 和时间。
- **先看优秀的同类作品**：做产品之前，先研究市面上做得好的是怎么设计、怎么写的。
- **MVP 思维先行**：最小可用版本先跑起来，后面再慢慢补齐。
- **站在用户角度**：多考虑真正使用的人的感受。
- **数据库表宁少勿多**（来源：AI 求职助手开发）：先根据 PRD 把核心表设计出来，表别开太多——表一多就容易理不清关系甚至 schema，后续加功能时自己都绕晕。
- **细节量化**：修改要求要给具体尺寸或相对比例，否则 AI 改很多轮都改不到点上。
- **给参照物**：AI 理解不了描述时，直接给参照物或图片。

## 4. 落地实例：先跑通闭环（来源：类测评网站项目）

做法：**先把整条闭环跑通，内容全部写死在前端，跑起来之后再迭代。** 第一版追求的是「能用」，不是「完备」。

## 5. 拓展功能 MVP 的需求分析要点（来源：给已有产品加新功能）

给已有产品加新功能时，需求分析要明确列出：

1. 用户完整使用流程
2. 需要新增哪些页面和路由
3. 需要新增哪些数据库表或字段
4. MVP **实现边界**与后续扩展功能

另外：AI 输出方案后自己先看一遍（重点看数据相关部分），这也是学习机会。

## 6. 第一版技术约定的实例（来源：AI 求职助手需求分析）

某个项目的真实技术约定，只作示范（**不是通用规则，要按自己的核心需求判断**）：

- 第 1 版先不用数据库，结果只保存在当前页面状态里（刷新丢失没关系）——因为这个产品的核心闭环是「一次性分析」，不需要留存
- API key 放环境变量，不写死在代码里
- 通用问题用现成的库解决（如 PDF 文字提取），不造轮子

判断标准见第 10 节：**优先选满足核心闭环的最简单方案**。

## 7. 长期视角（来源：踩坑记录·成本结构）

AI 能降低写代码的成本，但代码的阅读、测试、维护、加功能、二次开发的成本并没有下降。所以要让 AI 写的代码更规范，降低后续维护和拓展的难度——这也是划边界要认真的原因：MVP 不是乱写，是用最小的规范成本跑通闭环。

## 8. v2 修订（来源：一次真实实测评估）

在真实项目里实测发现，软约束不足以阻止代理抢跑（代理在 PRD 未确认时直接开始写页面代码），据此新增：

- **阶段门禁链**：三问 → mvp-plan 确认 → PRD 确认 → UI 结构确认 → 写码前检查清单，任何一道未过禁止写生产代码
- **PRD 默认必选**：原「若生成 PRD」的表述会被代理理解为可选，已改为默认必经，仅用户明确豁免可跳过
- **UI 结构设计门禁**：区分「不做过度视觉打磨」（限制投入）与「页面结构设计」（开发前必要检查点），精简为 5 项
- **阶段状态机**：状态字段记录在 mvp-plan.md，状态未切换不得进入下一阶段
- **产物分级**：文档稿 / UI 原型稿 / 生产代码
- **设计协同**：UI 阶段调用设计类 skill，避免页面模板化和 AI 味
- **诚实边界**：skill 是提示词级软约束，最后一道门禁永远是用户的确认动作

## 9. v2.1 修订（来源：实战营班班反馈）

三处规则被指出「过刚」，按实际开发场景放宽，同时补上两个流程缺口：

- **报错处理改为先诊断**：原「先退回稳定检查点」过于激进——报错未必意味着代码坏了，先回退会丢掉有效改动。新顺序：停 → 留现场（记录报错）→ 定位根因 → 最小修复一次 → 验证；**连续两次不中或改动开始扩散，才回退到稳定检查点重来**。口诀：错误局部、原因清楚就直接修；错误扩散、连改不中就回退。
- **技术取舍改为按需判断**：原「第一版不上登录/数据库/支付」是某个具体项目的结论，不是普适规则。改为「优先选择满足核心闭环的最简单方案」，默认省略这些组件，但当核心闭环离不开它们时（核心价值就是保存记录、多人协作等）第一版就该做，并在技术约定里写明理由。
- **新增增量模式**：已有产品上的小改动不再走完整六道门禁，复用项目里已确认的计划，只写「本次变化 / 影响范围 / 完成标准」三项，状态机走短路径（变更计划中 → 开发中 → 已验收）。
- **新增需求变更同步**：开发中确认要加的功能必须同步进计划——移入「需求变更记录」、补进最少功能清单、补齐完成标准；影响架构时同步更新 PRD。
- **新增试用反馈记录**：验收通过后追加一步，记录谁试用了、解决了什么问题、反馈是什么、下一轮优先改什么，作为扩展候选池排序的依据。

## 10. v2.2 修订（来源：同学反馈 + 开源技能 brainstorming 原版借鉴）

同学反馈指出守门员擅长「修剪细节」，缺「定调」（产品大方向发散与路线判断）。经研究开源技能 `superpowers:brainstorming` 原版（研究材料留存于工作区 `brainstorming-research/`），确认两者同源——原版精华不在「问什么」，而在**分类（路线档位）、授权粒度（阶段不传递）、反自我合理化（对照表）**三件事上。据此吸收 A/B/C 三组共 7 项：

**A 组 防抢跑强化**

- **自我合理化对照表**：把代理的危险念头逐条列出并给出「现实」，替换原先的祈使句式偏离信号。核心价值是**不给代理留解释空间**（原版最有效的装置）。
- **阶段授权不传递**：一次点头只授权被呈现的那一个阶段。批准计划 ≠ 批准 PRD ≠ 批准 UI ≠ 可写码；「方向对」这类回应不算批准。这是把授权**切碎**，而不是加更多禁令。

**B 组 需求理解与自审**

- **复述时区分「用户说的」与「我的假设」**：三问与 grill 追问的复述环节都要求分开写。假设不写出来，会成为后面返工的根源。
- **PRD 自审具体化为四项**：占位符扫描 / 内部一致性 / 范围检查 / 歧义检查。把原先笼统的「自己先审一遍」变成可执行、可验收的动作。

**C 组 路径与范围**

- **三档路径**：快速验证档（可行性小实验，产出是判断不是代码）/ 增量档（已有产品小改动）/ 完整档（新产品、新模块、结构级改动）。原先是二值（完整/增量），缺「先花半天验证能力边界」这一档——而这恰是 AI 应用开发最大的不确定性来源。
- **单向棘轮**：判据是项目而非熟悉度（新项目一律完整档）；中途发现复杂度超预期只能升级档位，永不降级；拿不准选更重的档。
- **多子系统先拆解**：需求包含多个独立子系统时先拆开、排顺序，只挑第一块走流程。在需要先拆解的项目上细化细节，是最贵的一种浪费。

**未采纳（记录决策）**

- **分节呈现 + 逐节确认**（原版每节问一次「到这里对吗」）：更严谨但会拉长流程，与守门员「轻量」定位冲突 → 不采纳，保留现有的一次性确认。
- **Visual Companion 浏览器可视化伴侣**（原版自带本地 server）：依赖外部脚本与浏览器环境，违背自包含 → 不采纳。
- **Spec 文件体系 / docs 目录约定**：已有 mvp-plan.md 作单一真源，不引入第二套文档。
- **对第三方技能的强制路由**（原版规定 brainstorming 之后只能调 writing-plans）：会把守门员绑死到某一开源生态 → 不采纳。
- **单元边界设计、既有代码库改进原则**：属实现深度，超出守门员职责 → 不采纳。

## 11. v2.3 修订（来源：v2.2 全流程 Codex 实测）

用「AI 小说导航工具」项目做了完整档 + 增量档双路径实测（2026-09-30），六个观察点五绿一黄。唯一漏洞：**完整档的写码前检查清单被整体跳过**——代理进入「开发中」状态后直接「更新文档、搭骨架、装依赖」，一行清单没输出就开跑了。

关键发现是**对照实验**：同一套机制在增量档守住了、在完整档失守了。差异不在内容而在形态——

- 增量档：3 项清单是「一句话自报」紧凑格式，紧跟分档声明，两者连成一个动作 → 生效
- 完整档：6 项清单是结构化列表，触发时机写在「写生产代码前」→ 「搭骨架/装依赖/更新文档」被归类为非生产代码的准备动作，门禁在写代码之前的所有动作里被绕过

据此修复（不是加粗语气，而是照已被实测验证有效的形态改）：

- **触发点改为状态触发**：状态切换为「开发中」后的第一条回复，必须先完整输出核对结果，之后才允许执行任何命令、写入任何文件、安装任何依赖。搭骨架、装依赖、改配置、更新文档明确写进「清单之后才允许的动作」。
- **自报格式改为一句话紧凑段落**：照增量档样式连成一段话，与分档声明连成一个动作，不拆成需要另起一屏的结构化列表。
- **自我合理化对照表补一行**：「先搭骨架、装依赖，这不算写代码」→ 骨架、依赖、配置都是实现的一部分，检查清单先于这一切。

教训沉淀：提示词级门禁的失效往往不是「模型不听话」，而是**触发条件里留了语义空隙**——「写代码前」这种按动作类型定义的时机，会被动作分类钻空子。改用**状态机位置**定义时机（进入某状态后的第一条回复），空隙即闭合。
