# MVP 原则参考（源自孙旺 林粒粒学院 AI 编程实战营 实战笔记）

本文件是 mvp-guardian skill 的理论依据，内容提炼自用户本人在 07_AI编程实战营 的笔记。监督与建议时引用这些实践经验。

## 1. 开发前三问（来源：vibe coding第二课）

开发前，先想清楚三件事：

1. 产品**最核心**的那一件事是什么？（比如一个 AI 翻译工具，就是输入一段文字，输出翻译结果。）
2. 至少需要什么功能？（需要一个输入框、一个按钮、一个结果显示框。）
3. 还有哪些影响用户体验的痛点？（这个等 MVP 跑通后，再考虑。）

> 先完成 MVP，再完美。

## 2. 开发流程顺序（来源：vibe_coding思路）

1. 明确需求
2. 生成 PRD 文档
3. 生成 UI 初稿
4. 代码生成（4.1 先写框架）
5. 调试迭代
6. 部署上线

注意事项：
- UI 设计参考图很重要。
- **不要着急写代码。**
- **先跑 MVP，别想一步到位。**

## 3. 经验教训（来源：经验教训.md，逐条为实战踩坑所得）

- **报错立刻回退**：一旦 AI 开发过程中报错，就立刻回退到上一步，不要在当前报错基础上进行更改，会错上加错。
- **PRD 自己先审一遍**：生成 PRD 后先看有没有遗漏、AI 是否理解到位，立刻修改，省 token 和时间。
- **先市场调研**：做产品先学习优秀作品的风格和文案。
- **MVP 思维先行**：最小化可用产品先行，后续再慢慢完善。
- **站在用户角度**：多考虑使用对象的体验。
- **数据库表宁少勿多**（来源：AI 求职助手开发）：先根据 PRD 把核心表设计出来（用户表、简历表、职位描述表、分析结果表），不要创建太多表——表太多容易理不清表关系甚至 schema，后续加新功能时自己无法理清。
- **细节量化**：修改要求要给具体尺寸/相对比例，否则 AI 改很多轮都改不到点上。
- **给参照物**：AI 理解不了说法时，直接给参照物或图片。

## 4. MVP 落地实例（来源：做出类SBTI测试网站）

> 第三个，也是 MVP 思维的体现：**先把闭环跑通，所有内容写死在前端，后面再迭代。**

## 5. 拓展功能 MVP（来源：给AI求职助手增加可收费功能）

加新功能时，需求分析要明确列出：
1. 用户完整使用流程
2. 需要新增哪些页面和路由
3. 需要新增哪些数据库表或字段
4. MVP **实现边界**和后续扩展功能

并且：codex 输出方案后先自己看一遍（重点看数据相关部分），这也是学习机会。

## 6. 第一版技术约定实例（来源：AI超级求职助手的需求分析）

第一版目标的技术约束示范：
- 第 1 版**先不用数据库**，结果只保存在当前页面状态里（刷新丢失没关系）。
- API key 放环境变量，不写死在代码里。
- 用现成的库解决通用问题（如 PDF 文字提取）。

## 7. 长期视角（来源：经验教训.md 第 14 条）

AI 能降低开发成本，但代码的阅读、测试、维护、增加功能、二次开发的成本没有下降。所以要让 AI 写的代码更规范，降低后续维护和拓展难度——这也是 MVP 划边界要认真的原因：MVP 不是乱写，是用最小规范成本跑通闭环。

## 8. v2 修订（来源：2026-09-28 Codex 实测评估，AI 网文大纲助手项目）

实测发现软约束不足以阻止代理抢跑（代理在 PRD 未确认时直接写页面代码），据此新增：

- **阶段门禁链**：三问 → mvp-plan 确认 → PRD 确认 → UI 结构确认 → 写码前检查清单，任何一道未过禁止写生产代码。
- **PRD 默认必选**：原「若生成 PRD」表述被代理理解为可选，已改为默认必经，仅用户明确豁免可跳过。
- **UI 结构设计门禁**：区分「不做过度视觉打磨」（限制投入）与「页面结构设计」（开发前必要检查点）；精简为 5 项：页面清单/信息结构、核心流程、四种状态、布局方向、交互与按钮文案。
- **阶段状态机**：计划中 → PRD 审查中 → UI 审查中 → 开发中 → 已验收/已暂停，记录在 mvp-plan.md 状态字段。
- **产物分级**：文档稿 / UI 原型稿（须标注）/ 生产代码（门禁全过才可写）。
- **报错处理升级**：停 → 回到最近稳定检查点（git commit）→ 讲清根因 → 一次只改一个原因 → 验证后继续。原「立刻回退上一步」保留本意但更安全。
- **设计审美协同**：UI 阶段调用 design-taste-frontend skill（taste-skill 仓库 v2），避免页面模板化和 AI 味。
- **诚实边界**：skill 是提示词级软约束，无法物理阻止抢跑；最后一道门禁永远是用户的确认动作，检查清单的作用是让抢跑可见。
